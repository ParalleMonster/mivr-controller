# MiVR 手柄

MiVR 将 Android 手机模拟成小米 VR / Oculus Go 的 BLE 手柄，支持运动指向、触控板和实体音量减键扳机。当前版本为 1.2.3，最低安装版本为 Android 8.0（API 26）。

在应用的连接页选择连接方式，然后从头显或小米 VR App 的「更换手柄」选择 `OMVR-V190`。通用 BLE 模式要求手机支持 BLE 外设广播。Android 13 起提供系统地址免六位码模式，需要 Root 和兼容的蓝牙配置。固定地址模式已在红米 K60 至尊版和小米 17 Pro 的指定蓝牙库版本上验证。

## 构建

使用 JDK 17 或 21、Android SDK 35 和 Gradle 8.9。

将 [Frida 17.26.0 Android ARM64 injector](https://github.com/frida/frida/releases/tag/17.26.0) 解压到 `.toolchain/frida-inject-17.26.0-android-arm64`。固定广播模式会核对解压文件的 SHA-256。

```powershell
gradle :app:assembleDebug
```

输出文件为 `app/build/outputs/apk/debug/app-debug.apk`。

## 早期版本的 BLE 测试记录

早期测试在红米 K60 至尊版启动广播，再用小米 17 Pro 上的 nRF Connect 扫描、连接并检查以下内容。

- 可连接的 Legacy 广播包含标准服务 `180A`、自定义服务 `81265652-3692-ae93-e711-270f223c83b3` 和厂商数据 `0x058E: 00`。设备名 `OMVR-V190` 放在扫描响应中。
- GATT 包含设备信息服务，以及两组自定义服务（4 个和 3 个特征）。设备信息服务使用实测的厂商、型号、硬件和软件版本，序列号使用测试值。
- 测试结束后点「停止广播」。广播名称使用系统蓝牙名称，应用会尝试恢复原名称。若应用被强制停止，重新打开即可触发恢复。

V0.2 增加了配对状态和 GATT 请求日志。「测试运动通道的加密订阅」默认勾选，要求连接加密后才能写入 `8126face` 和 `8126beef` 的通知配置。取消勾选可按 V0.1 的权限复测。该选项是根据原装手柄的已知加密行为设计的测试，实际配对仍由 Android 系统蓝牙栈处理。自定义值和运动数据仍待实现。

## 实机验证

2026-11-08 在 Android 16 的红米 K60 至尊版上通过 ADB 安装。Windows 蓝牙扫描到可连接的 `OMVR-V190`，确认两个广播服务和 `0x058E: 00`。电脑两次成功连接，发现两个自定义服务、7 个特征及其属性、8 个描述符，并读到固件版本 `2.7.1`。停止广播后，蓝牙名称恢复为 `Redmi K60 Ultra`。

电脑还发现红米系统公开的其他 GATT 服务。原装手柄本次广播的厂商数据为 `01`，并带有 `Classic Not Supported` 标志。模拟版的厂商数据复现较早采集的 `00`，本次扫描只报告 `General Discoverable` 标志。

同日，小米 17 Pro 的 nRF Connect 通过扫描连接到红米，并在未绑定状态下读到型号 `OMVR-V190`、测试序列号 `MIVR-TEST-01`、固件字段 `2.7.1`。已核对两个自定义服务、7 个特征的属性及描述符。对 `189a54f9` 启用通知后，读取 CCCD 返回 Notifications enabled；取消后读取返回 Notifications and indications disabled。测试结束后已从 17 Pro 断开连接，红米由用户操作。

17 Pro 最初尝试了扫描列表中的历史地址，连接未成功。重新扫描后，使用新地址连接成功。因此复测需使用新扫描到的地址。

2026-11-09，用户报告小米 VR 尝试连接 V0.1 时提示 PIN 码错误。复测中，红米日志确认头显 `v1o-5D4E` 建立了 BLE 连接，并进入 LE Secure Connections 的数字比对（Android 配对类型 `2`）。01:42:25 红米侧提交了确认，随后等待对端的 DHKey 检查消息，至 01:42:51 以 `SMP_RSP_TIMEOUT` 结束。另一次重试以 `SMP_CONN_TOUT` 结束。已观察的尝试最终均回到 `BOND_STATE_NONE`。

用户确认头显的手柄配对界面不显示验证码。原装手柄以指示灯提示配对，没有数字显示。下一步对比原装手柄与模拟版的 SMP Pairing Request / Response，重点查看 I/O Capability、OOB 和 AuthReq，以确认头显正常使用的配对方式。

通过 ADB 重启红米蓝牙后，完整 HCI 日志开始写入。2026-11-09 01:58 至 01:59（香港时间），头显的 Pairing Request 和红米的 Pairing Response 连续三次均为 `KeyboardDisplay`、`OOB=0`、`AuthReq=0x0D`、最大密钥长度 16 字节。`0x0D` 表示请求绑定、MITM 保护和 LE Secure Connections。按蓝牙规范，这组参数选择数字比对。红米侧的系统日志再次记录了 `SMP_RSP_TIMEOUT`。

可使用 `node tools/read-smp.mjs <btsnoop_hci.log>` 提取配对能力、认证标志、失败原因和 DHKey Check 的方向。脚本以 UTC 输出时间，也支持从标准输入读取。当前红米 ROM 在抓包时间字段中写入了本地时间，解析该机记录时传入偏移 `+08:00`。

红米可记录自己参与的连接。当前头显无法通过 ADB 读取日志，现场没有 BLE 嗅探器，用户选择保留原装手柄与头显的配对。原装手柄的实际配对字段仍待采集。

### 无屏幕配对实验

经用户确认，在红米上运行了 120 秒的临时蓝牙配置测试。2026-11-09 02:14（香港时间），红米的 Pairing Response 为 `NoInputNoOutput`、`OOB=0`、`AuthReq=0x09`。双方交换 DHKey Check，红米系统确认 LE 加密成功并进入 `BOND_STATE_BONDED`。实验结束后，蓝牙重新启动，脚本通过哈希验证原配置已恢复。

用户报告头显仍显示「未找到可连接的手柄」。绑定之后，头显在抓包的 02:14 这一分钟内对特征 `8126a920` 的 ATT 句柄 `0x00B0` 发出了 251 次 Read Request。V0.2 对应返回了 251 次 ATT 错误 `0x06`（Request Not Supported）。应用日志记录了整个测试窗口的 723 次 `8126a920` 读取，没有记录运动通道订阅。下一步确认原装手柄对此特征的真实返回值及其格式。

### 固件分析与 V0.3

从小米 VR 1.1.281 更新包提取了 `system` 分区。内含原装手柄 2.7.1 镜像 `remote_firmware_v190_cnc.img`。镜像在文件偏移 `0x8030` 附近定义了 `8126a920` 属性，最大长度为 13 字节，用户描述符为 `Status`。头显侧 `libbleremote.so` 的 `Pacific::DecodeDeviceState`（`0x34cd4`）要求正好 13 字节，读取第一个字节作为电量百分比，并把高于 100 的值限制为 100。

V0.3 现在会成功响应 `8126a920` 读取，返回 13 字节。首字节为红米电量百分比，获取失败时使用 100。其余 12 字节在该解析函数中没有读取，V0.3 暂填零。这个状态包还需要在头显上验证，随后才能判断是否有其他手柄特征需要实现。

2026-11-09 02:39（香港时间），V0.3 在临时 `NoInputNoOutput` 配置下通过加密绑定。头显读取 `8126a920` 一次，收到 13 字节响应，随后成功写入 `8126beef`、`8126face` 和 `8126a920` 的订阅配置。头显也尝试读取校准特征 `81261d57`，V0.3 返回 ATT `0x06`。应用目前没有发送运动或按键数据。实验结束后脚本验证红米原蓝牙配置已恢复。

### 运动数据与 V0.5 免六位码配对

V0.4 加入 `8126beef` 三组陀螺仪样本及 `8126face` 加速度、磁场、触控和按键通知。两个包都是 20 字节，比例和布局来自头显 1.1.281 固件的解码函数。运动传感器在头显订阅后启用。当前使用 Android 原始坐标轴，握持方向和头显中的光标响应待实机校验。

2026-11-09 02:48（香港时间），V0.4 在临时免六位码配置下完成了绑定。抓包显示头显读到 `81261d57` 的 18 字节响应，其首字节是原装手柄工厂校准读失败时使用的 `0xFF`。这次头显没有写入通知订阅，用户报告光标和按键均无反应。V0.5 恢复 V0.3 的 ATT `0x06` 校准读取响应，保留运动和按键通知实现。

V0.5 的「免六位码配对（需 root）」适用于已 root 的红米 K60 至尊版 Android 16 测试环境。在 APatch 中允许 MiVR 手柄获取 root 后，应用临时加载 `NoInputNoOutput` 配置，重启蓝牙并自动广播。请在两分钟内用头显连接。点「停止广播」可提前结束，或等待窗口自动关闭。结束时再次重启蓝牙并通过哈希核对原配置。脚本随 APK 打包，源文件在 `app/src/main/assets/redmi-headless-pairing.sh`。

2026-11-09 02:52（香港时间），从 V0.5 的按钮启动测试并在准备阶段提前停止一次，红米成功恢复原配置。第二次测试中，应用自动开始广播，头显完成免六位码绑定并订阅两个运动通道。红米抓包在约 47 秒内记录到每路 2531 条 20 字节通知，约每秒 53 条。`8126face` 中捕捉到 Oculus、扳机、触控板按下和触摸的标志。用户确认头显有操作反应。

### V0.6 保持手柄会话

V0.6 将广播、GATT 连接和传感器移到 Android 已连接设备前台服务。按返回或回到桌面后，从桌面再次打开 MiVR 可回到当前会话。「免六位码配对」仍等待最多两分钟。首次运动通知成功发送后，会话保持到用户点「停止广播」或系统结束应用进程。恢复蓝牙前会先停止广播和运动通知，避免 V0.5 在重启蓝牙时触发的蓝牙服务进程异常。

2026-11-09 03:00–03:01（香港时间），红米运行 V0.6，头显免六位码配对后订阅两个运动通道。应用页面两次离开并重新打开，抓包中仍只有一次 BLE 连接和一次 SMP 配对，运动通知持续发送。

### V0.7 恢复被系统结束的会话

HyperOS 在最近任务里划掉 MiVR 时会强制结束应用和它的 root 脚本。V0.7 将正在使用的配置和原文件哈希保存在 root 私有目录，使用进程退出后自动释放的文件锁。再次打开 MiVR 会检查上次成功的免六位码会话，核对并清理旧挂载，再自动开启广播。点「停止广播」会取消下次自动恢复。

红米抓包确认，`OMVR-V190` 的广播使用可解析私有地址，重新启动广播时可获得不同地址。头显配对时，红米发送身份解析密钥和公开身份地址。V0.7 保留系统的地址选择。普通退出页面沿用已经建立的连接，被系统结束后需要建立新的 BLE 连接。

V0.7 实机验证了强制结束后的自动广播。头显在红米恢复广播后仍需手动连接。小米 VR 配套应用在两次连接中显示的地址均与红米抓包中的私有广播地址吻合。两次配对的公开身份地址相同。

### V0.8 固定广播地址

在已安装 APatch 的红米上，「免六位码 · 固定地址」会临时禁用红米系统的 BLE 地址隐私设置，使用适配器自己的公开地址广播。点「停止广播」会恢复该设置和原配对配置。若系统结束 MiVR 进程，再次打开应用会优先接管仍生效的临时配置，保留蓝牙进程并为已绑定设备恢复之前的运动订阅。

### V0.9 恢复免六位码配对

V0.8 的实机抓包确认使用了公开广播地址。用户报告免六位码失效，本次保留的抓包中没有头显发起的配对。已通过 ADB 核对并恢复红米的原蓝牙设置。V0.9 的「免六位码配对」恢复到之前在同一头显上验证过的配对方式，使用系统默认的地址策略。首次启动免六位码会话时也会清理 V0.8 可能留下的固定地址设置。

2026-11-09 09:16（香港时间），V0.9 实机配对成功。红米的 SMP 响应为 `NoInputNoOutput`，双方交换了 DHKey Check，红米进入已绑定状态。头显成功订阅两个运动通道，抓包记录到每路约每秒 70 条通知。

### V0.10 为 MiVR 单独指定广播地址

免六位码会话通过 root 广播进程为 MiVR 请求适配器的公开地址。SMP 配对沿用 V0.9 的临时配置，系统的 BLE 隐私设置保持原样。如果设备拒绝这项广播请求，应用会退回系统地址并在界面中显示实际模式。普通「开始广播」仍由 Android 选择地址。配套应用保留旧的私有地址时，首次切换到公开地址需要选择一次模拟手柄。

2026-11-09 09:29（香港时间），V0.10 两次成功启用公开地址广播，Windows 扫描也确认收到 `OMVR-V190`。第二次测试中，头显发起了经典蓝牙连接，红米产生了 HCI User Confirmation Request，随后弹出六位数字比对。这次抓包没有头显发起的 LE 连接。原装手柄的广播包含「BR/EDR Not Supported」标志。红米这版 Android 的应用广播接口会生成 Flags 字段，无法指定这个标志。

V0.11 默认回到 V0.9 已验证的免六位码 BLE 广播路径。「实验性固定地址」单独保留为测试选项，默认关闭。固定地址与免六位码尚未在同一次头显连接中得到验证。

2026-11-09 09:39（香港时间），V0.11 默认模式通过实机配对。用户确认未弹出六位码，抓包确认红米响应 `NoInputNoOutput`，头显订阅两个运动通道后持续收到数据。

### 静态随机地址测试

红米这版蓝牙库中的广播地址生成函数可在运行时为 MiVR 指定静态随机地址。带独立测试标记的可连接广播在同一台红米上启动两次，HCI 两次都将广播组的地址设为 `F2:6A:A7:11:53:CB`，广播组地址类型仍为 Random。公开地址和系统隐私设置都保持原样。这个结果只验证了红米的广播地址，头显的配对及重连需分别实测。

随后用 MiVR 实际使用的厂商数据 `058E:00` 和手柄服务 UUID 再启动两次可连接测试广播。两次的 HCI 地址类型均为 Random，地址同为 `F2:6A:A7:11:53:CB`。

2026-11-09 11:15（香港时间），实机 V0.11 重建广播后，Windows 扫描到 `OMVR-V190` 使用 `F2:6A:A7:11:53:CB`。头显断开原连接后建立了新的 LE 连接。HCI 的 Advertising Set Terminated 事件将新连接与该静态地址广播组关联。红米以 `NoInputNoOutput` 完成绑定，头显成功订阅两个运动通道，用户确认未弹出六位码。

两次重开 V0.11 时，红米都以相同静态地址重新广播。抓包显示 LE 链路保持在线，两个运动通道仍在发送。用户报告第一次可以使用，第二次头显显示已连接但输入无反应。两次重开时，首个运动包计数都重新从 10 开始。V0.12 改用红米的单调运行时钟生成运动包计数，使进程重启时仍沿用同一时间基准。该改动能否解决头显输入停滞，需要复测。

V0.12 实测两次重开后运动包计数均按时间间隔延续，头显仍出现显示已连接但输入无反应。V0.13 将广告状态、蓝牙连接和运动通知状态分开显示。广告回调晚于连接回调时，界面也会保留已连接状态。运动状态统计红米成功发送的通道数。

### V0.14 固定地址与免六位码

在当前这版红米 K60 至尊版 Android 16 蓝牙库上，勾选「固定手柄地址」，再点「免六位码配对（需 root）」。应用通过 APatch 启动已验证的广播地址探针，使用 `F2:6A:A7:11:53:CB` 广播，并沿用系统的配对身份。首次切换时可在小米 VR 中更换一次模拟手柄。点「停止广播」后，应用结束探针并恢复蓝牙配置。取消勾选后仍可使用系统地址的免六位码模式。
